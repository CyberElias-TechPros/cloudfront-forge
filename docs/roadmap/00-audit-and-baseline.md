This document answers three questions with evidence rather than opinion:

1. What is actually built and verified today?
2. What blocks the product from being _excellent_ — for the web audience, and for a real native Android audience?
3. Which of those items are launch blockers, which are differentiators, and which are polish?

Nothing in §1 is claimed unless it was executed in this workspace on 2026-10-21 with the
command shown. Nothing in §2 is a wish-list: each finding has a file/line anchor, a
user-facing consequence, and a task that closes it.

### What this baseline means

- The **web + API product is real and internally consistent**: 303 behavioural worker
  tests over a real SQLite schema is a genuine asset, and the API is a good target for a
  native client because auth is bearer-token based, CORS is not required for native
  callers, and responses are enveloped (`{ success, data }`).
- The **"cheat-resistant" claim is the weakest link** (see F-01/F-02): a member can
  self-report watch seconds when YouTube isn't connected, signed watch sessions are
  disabled in production, and recorded heartbeats are never read.
- **Android does not exist**, and several platform primitives it depends on (device push
  tokens, idempotent writes, a contract artefact, user blocking) do not exist either.
  This is why the roadmap starts with platform work rather than with screens.

## 3. What is genuinely good (protect these)

These are assets the roadmap must not break while everything else changes:

1. **The reward ledger discipline.** Conditional `UPDATE ... WHERE status = ...`, `balance_after`
   on every ledger row, spend+effect in one `db.batch`. Tests assert pay-once under replay.
2. **Behavioural worker tests over real SQLite.** 303 tests apply all 37 migrations with
   foreign keys on. This is the safety net that makes aggressive platform work affordable.
3. **A single routing table** (110 entries) that tests assert is reachable.
4. **Entry-point account gate** (`ACCOUNT_DELETED/…`) — one place, consistent 403s.
5. **Zod-validated payloads written verbatim, sanitised at the boundary**, with a
   repo-hygiene test that fails the build if a credential is committed.
6. **The public landing experience** (`src/routes/index.tsx`) is distinctive, fast, and
   already carries the honest positioning the product needs ("real watch time, useful
   feedback, no growth theater").
7. **`DELETE /users/me` closing every open loop** — most products discover this at audit time.

## 4. Judgement: what "highest possible potential" means here

The product does not fail on features; it fails on three things:

1. **Proof.** "Verified attention" is not yet verified. Until F-01/F-02/F-04 are closed,
   the honest landing copy is ahead of the implementation, and the leaderboard rewards
   whoever scripts best.
2. **Distribution.** The audience lives in WhatsApp groups on Android phones with metered
   data. A Vercel SPA behind a Google-popup sign-in is a poor first touch in that
   environment; a native app with Google Credential Manager, offline queue and FCM push is
   the right first touch.
3. **Measurement.** Without analytics/crash reporting, every improvement after this
   roadmap is unverifiable — the roadmap therefore front-loads instrumentation before
   growth work.

Everything in the phase plan follows from those three statements.
